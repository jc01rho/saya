# Optional PirateTalk extension contract

Task1 adds contract tooling only. No optional actions or transport routes are
mounted. The upstream core owns `piratetalk-rs/contracts/piratetalk-extension.openapi.json`
and its fixture corpus; the copies here are byte-identical. Canonical Kakao/Tsuba
contracts, hashes, generated output and provider identities remain unchanged.

Run `bun run extension:generate` after copying an updated core contract and
updating its separate pin. It writes only `src/contract/piratetalk/`. The existing
canonical generator is reused as an in-memory compiler, without adding the
extension to its canonical registry. Extension enums are not widened: unknown
send and outcome discriminants must fail closed.

Run `bun run extension:check` to check both pins, regenerated bytes, all endpoint
corpus coverage and acceptance/rejection. It never writes files, even in a dirty
worktree. Unexpected generated artifacts fail. To also verify the core copies:

```sh
bun run extension:check -- --core-contract /path/to/core/piratetalk-rs/contracts/piratetalk-extension.openapi.json
bun run contract:check
bun test tests/contract/extension.test.ts tests/contract/generation.test.ts
```

`--fixture /path/to/payload.json` checks a `{schema,data}` envelope through the same
generated boundary. A malformed envelope, unknown schema, invalid payload or bad
CLI flag exits nonzero; the final success line is emitted only after every check.

Consumers must use generated `validateExtension(name, value)`, not the raw Ajv
validators alone: the boundary also checks i64 ID ranges, ordered periods,
mention scalar boundaries/overlap, mutually exclusive history anchors and cursor
progress. Inputs are never coerced or mutated. Multipart fixtures exercise shape;
actual byte caps/content sniffing and source/cursor/account checks are server
responsibilities, not proven by JSON fixtures.

The prefix is `/extensions/piratetalk/v1` on the same core through the existing
same-origin `/api` proxy. Discovery is once per session/reconnect, not polling.
404 means canonical-only, 401 is authentication failure, malformed/incompatible
discovery disables optional actions with a diagnostic. No second provider or SSE.

The extension declares a new single-file 64 MiB ingress policy. Retained native
upload code has no explicit size cap or MIME allowlist; the 64 MiB media proxy cap
is not an upload limit. Retained upload dispatch also sends: task6 must stage
first and consume the token through the singleton send gate. No album fallback.
Periods are inclusive Unix seconds with no fixed retained duration maximum.
The wire caps timestamps at JS safe integer maximum and rejects inverted ranges.
Model names require the configured discovery allowlist, never client credentials.

Exact baseline service traceability, readiness dependencies and native limitations
are in the core-owned `piratetalk-rs/contracts/piratetalk-extension.md`. In
particular, `question::post_room_question` calls the model but currently limits
retrieval to4,000 rows and context to80; task9 must address full-period coverage.
Code presence does not establish operational readiness or native delivery.
